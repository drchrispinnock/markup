# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Markup is a native macOS plain-text editor, written in Swift with AppKit, that will eventually edit Markdown. The scope ends there: the document stays plain text and the editor won't do anything beyond that.

## Building, running and testing

It is a Swift Package (no Xcode project), built with the Command Line Tools:

- `swift build` builds the app.
- `swift run` builds and launches it as a bare executable. Debug builds embed `img/Markup.png` in the executable's `__TEXT,__markup_icon` section (`Package.swift`), and `DevelopmentIcon` draws it as the app icon when there's no app bundle, cropped and clipped the way the icon script does it.
- `scripts/build-app.sh` makes `build/Markup.app`: a release build, `Info.plist`, `Sparkle.framework` in `Contents/Frameworks`, and `AppIcon.icns` generated from `img/Markup.png` by `scripts/make-icon.swift`, all ad-hoc signed. The icon script makes the artwork's white surround transparent and clips it to exactly an 824×824 rounded rect (radius 185) at (100, 100) on a 1024 canvas. macOS 26 shows any other outline shrunk onto a grey plate.
- `scripts/release.sh` makes a release: a universal app (`UNIVERSAL=1 scripts/build-app.sh`) signed with the Developer ID in the keychain and the hardened runtime, in `build/Markup-<version>.dmg`, notarized (keychain profile `NOTARY_PROFILE`, default `listful-notary`) and stapled; then the stapled app zipped into `build/releases/<version>/` and its entry added to `appcast.xml` (the feed, served from the repo's `main`), signed with the EdDSA key in the login keychain. Both files go in a GitHub release tagged `v<version>`. `--adhoc` tests the packaging without signing or notarizing. Bump `CFBundleVersion` first; Sparkle compares it.
- `swift test -Xswiftc -plugin-path -Xswiftc /Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/testing` runs all tests.
- Add `--filter ListEditorTests/tabNestsAndShiftTabUnnests` to run a single test.

The `-plugin-path` flag is needed: the Command Line Tools keep the Swift Testing macro plugin in `plugins/testing/`, and the build doesn't reliably search there. Without the flag, test builds fail intermittently with "plugin for module 'TestingMacros' not found".

The machine has only the Command Line Tools, not full Xcode. They lack SwiftUI's macro plugins, so `@State` and other SwiftUI macros fail to compile. That is why the UI is plain AppKit; don't introduce SwiftUI unless full Xcode is installed.

## Targets

- `MarkupCore` is pure Swift with no AppKit. `BlockStyle` is the line styles (raw value = heading level, `heading1` to `heading6`, titled Heading 1 to 6; 0 = paragraph, -1 = code, -2 = table cell, -3 = quote, -4 = front matter). `ListItem` (level + `ListMarker`: bullet / unchecked / checked / numbered, a number, and `written`, the prefix as read) is a list line. `MarkdownCodec` converts Markdown to and from `[Line]`, losslessly. It recognises `#` to `######` + space, and `- `, `- [ ] `, `- [x] `, and `1. ` or `1) ` (one to nine digits), and `> ` (up to three spaces, then `>` and a space if there is one) for a quote line, whose text isn't read further and which keeps the prefix it was read with (`Line.quotePrefix`, not compared); lines following a quote without their own `>` are paragraphs, though CommonMark would carry the quote on. List items nest as CommonMark has it (`ListContext`): an item indented from the text of the item above to three columns more is nested in it, and with no list open, an item may be indented up to three spaces. An item made anew is written indented to the text of the one it is nested in (so three spaces under `1. `, two under `- `); one read keeps its prefix. A paragraph that would read as an item there is escaped (`\- `, or `1\. ` after the digits), and one that would read as a quote too (`\>`). Lines between a ```` ``` ```` fence (with any info string, such as a language) and the next line of exactly as many backticks are `.code` lines kept verbatim; the first carries the `CodeFence` so it is written back as it was, and the fence is lengthened if a line inside would close it. Front matter (Jekyll's, Hugo's and Pandoc's YAML header: a first line of `---`, not followed by a blank line, up to the next `---` or `...` line, spaces and tabs allowed after each) is `.frontMatter` lines kept verbatim, which nothing reads as Markdown (YAML comments start with `#`), and `MarkdownCodec.frontMatter(in:)` splits it off. GFM tables (`MarkdownTable`: a header row and a delimiter row with the same number of cells, then rows up to a blank line, a line without a pipe or another block) are `.table` lines kept verbatim; `MarkdownTable.table(from:)` and `lines(for:)` convert them to and from cells and alignments. A heading's ID (`Line.anchor`, a `HeadingAnchor`) is `{#id: x}` or `{#x}` alone on the line above it, or `{#x}` at its end (Pandoc's form), but not both: with one at its end, the line above stays text. An anchor keeps the text it was read from (`written`), so it is written back exactly while its ID is unchanged. `HeadingReference` reads a link destination that goes to a heading (`#id`, or `path#id` with no URL scheme), and `occurrences(inMarkdown:)` lists a file's links to headings, in order. `MarkdownCodec.headingIDs(inMarkdown:)` is a file's heading IDs. `HeadingIDScheme` makes new IDs: `fileLevelWord` (`170_dapps_2_Setting`: the file's name, level and first word up to ten characters, then `_2`, `_3`...), `hash` (8 hex digits, FNV-1a) or `slug` (`setting-up-my-dapp`, then `-1`, `-2`...), each avoiding a set of IDs taken. Text that would otherwise read back as one of these is escaped with a backslash (`\# `, `\- `, `- \[ ] `, `` \``` `` when a closing line follows, `\{#x}` above a heading or ending one). `InlineMarkdown` reads and writes a line's `**bold**`, `*italic*`, `~~strikethrough~~`, `` `code` ``, `H~2~O` (subscript), `x^2^` (superscript), `==highlight==` and links, `[text](destination)` (`InlineSpan.link`; the destination can be any reference), as `InlineSpan`s, matching delimiters much as CommonMark does (code spans first, then emphasis with the rule of 3). Tildes pair like asterisks: a run pairs with one of the same length, except that a run of three splits into strikethrough and subscript (`~~~x~~~` is both). Subscript and superscript follow Pandoc: allowed inside words, but not across whitespace, so `x^2 + y^2` stays text. Underscores aren't emphasis. A link's text is parsed on its own (no links inside links), and a link title isn't kept. `MarkupTag` reads a tag: a variable, `<!-- MARKUPTAG name-->value<!-- ENDMARKUPTAG -->` (variables were once called tags, hence the comment), or a citation (`kind`), `<!-- MARKUPBIBTAG R-1 -->[1]<!-- ENDMARKUPBIBTAG -->` (its comments kept as written); `tags(in:)` finds them in a line, `updated(from:)` takes a value from `TagSources` (the variables and bibliography, either missing), and `updating(markdown:from:)` sets a file's values and rewrites its bibliographies, except in front matter. Code shows comments (Leanpub's too), so a fenced block with variables is written with their values as plain text, after a comment holding the block as a template (`CodeTemplate`: `<!-- MARKUPCODE`, the lines with `@name@` for each variable, `@@` for `@` and `--@>` for `-->`, then `-->`, on the line before the fence); read back, the block's `.code` lines hold the variables' Markdown, the values read from the block. A block that no longer fits its template (edited elsewhere) is read as plain code, and the template stays as a comment. `pieces(of:)` reads templates too, and treats a comment's lines as text. Citations in code stay as written. `Bibliography` reads a `bibliography.txt` (`SEC|title` starts a section; any other line is an entry, numbered from 1 in order: just its text, keyed by its FNV-1a hash (`key(for:)`, `HeadingIDScheme.hash`), or `key|text` when what comes before the first `|` can be a key) and writes it (`markdown(hanging:)`): between `<!-- MARKUPBIBLIOGRAPHY -->` and `<!-- ENDMARKUPBIBLIOGRAPHY -->` lines, each section's title in bold, then `[n] text` paragraphs, optionally inside Leanpub's `{begin-hanging-paragraphs}` / `{end-hanging-paragraphs}`; `normalized` makes one read from a file comparable with one written anew. `VariableFile.values(from:)` reads a `variables.txt` (`name|value` lines; blank lines, `#` lines and further fields ignored), and `values(fromFiles:)` merges those of `VariableFile.names` (`variables.txt`, then for now `tags.txt`), the first file with a value for a name giving it. The inline parser and writer keep a tag whole (`InlineMarkdown.wholeRanges`), before comments, then HTML tags, so their attributes aren't read as emphasis or escaped. `HTMLTag` reads the few HTML tags the editor shows, `<br>`, `<img>` (with a `src`; `image` is its `src` and `alt` as a `MarkdownImage`), `<p>` and `</p>`, and the formatting tags `HTMLFormat` names (`<strong>`/`<b>` bold, `<em>`/`<i>` italic, `<h1>`–`<h6>` heading), opening and closing, in any case, with their attributes, not after a backslash; `MarkdownImage.image(written:)` reads an image written either way. `HTMLFormat.ranges(in:tags:)` gives the stretches of a line between each opening formatting tag and its closing one, with their formats; an unclosed tag does nothing. `MarkdownImage` reads `![alt](path)`, and `LinkDestination` the `(destination "title")` part both use. `HTMLComment` finds `<!-- -->` comments, which the inline parser and writer keep whole; the codec keeps a comment spanning lines with the line it starts on, so that `Line`'s text holds newlines. Tested by `MarkupCoreTests`.
- `Markup` is the app executable. `MarkupTests` drives a real `EditorViewController` through NSTextView commands (`insertText` one character at a time, `doCommand(by:)`) and the style popup's action, with manual undo groups standing in for events.

## Architecture

The app uses AppKit's document architecture. `NSDocumentController` (never subclassed) creates documents and their windows and handles the File menu, unsaved-changes prompts and quitting. Markdown (`net.daringfireball.markdown`, `.md`/`.markdown`) is the main document type. Any plain text (`public.plain-text`, handler rank Alternate) opens too, because an app that declares its own type for `.md` takes over from `net.daringfireball.markdown` on that Mac, and those types conform to plain text.

- `Info.plist` (repo root) declares the document type and names `MarkdownDocument` as its class. With no app bundle, `Package.swift` embeds it into the executable's `__TEXT,__info_plist` section with a linker flag, and that is where `NSDocumentController` reads it from. Adding a file type means editing this plist.
- `MarkdownDocument.swift` holds the Markdown read from disk, as UTF-8 with CRLF converted to LF. It owns its `EditorViewController` (`editor`, made on first use from that Markdown) and asks it for fresh Markdown when saving. The editor is shown either by a `DocumentWindowController` (the document's own window, from `makeWindowControllers`) or by a project window, never both. It has `@objc(MarkdownDocument)` so the plist can name it without a module prefix. `autosavesInPlace` is off, to keep classic Save / Save As behaviour.
- `main.swift` starts `NSApplication` by hand (there is no nib or app bundle) and sets the activation policy to `.regular`, so that a process launched by `swift run` gets a Dock icon, a menu bar and focus.
- `MainMenu.swift` builds the menu bar in code. The app menu uses the standard About panel, which reads its name, version and icon from the bundle. File > Open Recent is built by `AppDelegate` (`AppDelegate+Recent.swift`, the submenu's delegate) each time it opens, not by AppKit, whose own would open a project folder as a document: `NSDocumentController`'s recent files, then the recent projects (`Settings.recentProjects`, key `MarkupRecentProjects`, most recent first, at most 10, noted by `openProject(at:)`; folders that have gone are left out), then Clear Menu. Each item shows its name, then dimmed the folder it is in (`recentLocation(of:)`: from `~`, the middle left out past 50 characters), since Leanpub books' folders are all called `manuscript`. The Insert menu has Link…, Cross Link…, Table…, Image…, Variable…, Citation…, Bibliography and Update Variables in Project. View > Show Markdown (⇧⌘M) reaches `EditorViewController.toggleMarkdown(_:)` through the responder chain. View > Show Line Numbers (⇧⌘L, `toggleLineNumbers(_:)`) turns `Settings.showsLineNumbers` on or off for every editor. Menu items have a nil target and send standard selectors (`newDocument:`, `save:`, `saveAs:`, `performClose:`, `undo:`...) along the responder chain. The Edit menu has to exist for Cmd-C/V/Z/A to reach the text view. Edit > Find (⌘F, ⌥⌘F replace, ⌘G / ⇧⌘G) sends `performTextFinderAction:` with the `NSTextFinder.Action` as the tag; the text view has `usesFindBar`, so it shows the standard find bar above the text. In the Formatted view it searches the text as shown, without Markdown markers. Edit > Go To Line… (⌘L; ⌘G stays Find Next) shows `GoToLineController` at the caret ("Line:", a number field, "of" the number of lines, and Go), and `goToLine(_:)` selects that line of the Markdown, the last line if past the end, numbered as the Markdown view's line numbers are. In the Formatted view it selects the text showing that line (`textLocation(ofMarkdownLine:)`, which switching views also uses): the item without its marker, a table row's first cell (the header for the delimiter row), and for front matter the start.

### Editor model

`EditorViewController` (an `NSViewController`, in the responder chain after its views) is split across files: views, invariants and undo helpers in the main file; `+Markdown` (load / save / copy); `+Styles` (popup, heading Return, typing attributes); `+Lists`; `+Shortcuts` (typed Markdown syntax); `+Emphasis` (bold, italic, strikethrough, code, subscript, superscript and highlight buttons and Format menu); `+Links`; `+Code` (code blocks, Reload Images, and `EditorLayoutManager`, which shades code blocks and draws quotes' bars); `+Quotes` (blockquotes); `+Tables` (tables as `NSTextTable` grids); `+HeadingIDs` (hidden heading IDs, added on save); `+CrossLinks` (links to headings); `+BrokenLinks` (links to missing headings); `+Tags` (variables from `variables.txt`, citations and bibliographies from `bibliography.txt`); `+Images` (Insert Image button); `+FrontMatter` (the front matter badge, and `BadgeButton`); `+ViewMode` (Formatted / Markdown switch, line numbers); `+GoToLine` (Edit > Go To Line). `EditorTextView` is an NSTextView subclass that forwards marker clicks and lets the controller write and read the pasteboard (`plainTextForCopy`, `pasteHandler`). A plain text view writes and reads the legacy `NSStringPboardType` (`legacyStringType`), which isn't equal to `.string`, so both are checked for. It also owns the spelling and grammar settings: the Edit > Spelling and Grammar toggles are NSTextView actions, which it overrides to save the settings in `checkingDefaults` and post `.markupCheckingDefaultsChanged`, so every editor sharing those defaults follows. Defaults: spelling and grammar on, autocorrect off. Tests give editors a throwaway `UserDefaults` suite. It uses TextKit 1 (`usingTextLayoutManager: false`) so the layout manager can hit-test markers.

The text view never contains Markdown markers. A line's style lives in attributes on every character of the line, including its newline:
- **Headings:** `.blockStyle` (`BlockStyle+AppKit.swift`) plus the matching font. The style popup offers Headings 1 to 3; it shows 4 to 6 (hidden items) on their lines, but only typing `####` to `######` makes them.
- **List items:** the line starts with one U+FFFC attachment character carrying `.listMarker`, which draws the bullet or checkbox (`ListItem+AppKit.swift`, drawn with a handler so colours follow dark mode), or a number (`NumberMarkerCell`, `ListItem.numberWidth` wide). A numbered item's number isn't stored but worked out when drawn and saved (`listNumber(atLineStart:)`): the list's first item's `.listNumber` (as read or typed), counting on for each numbered item above at the same level, deeper items not counting; a line that isn't an item, or an item at that level that isn't numbered, ends the list. It shows as `1.` at level 0, `i.` at 1, `a.` at 2, and round again (`numberText`), but is always saved as digits, since Markdown has no others; edits redraw the numbers below them (`redrawListNumbers`). Typing `1. ` (or any number) starts a list from that number. Every character of the line carries `.listLevel` and an indented paragraph style. Even an empty item therefore has a character to hold its attributes.
- **Bold, italic, strikethrough, inline code, subscript, superscript and highlight:** `.inlineBold`, `.inlineItalic`, `.inlineStrikethrough`, `.inlineCode`, `.inlineSubscript`, `.inlineSuperscript` and `.inlineHighlight` on the characters (`InlineStyle+AppKit.swift`). The font comes from the line's block style plus these (code is monospaced, subscript and superscript smaller and shifted with `.baselineOffset`), so wherever a line's style attributes are set, `applyInlineStyles(in:)` must follow to put the right font, strikethrough line, background (yellow `highlightColor` over code's shading), baseline offset and link colour back. Highlight has a Format menu item but no button (`button(for:)` is nil).
- **Links:** `.markdownLink` (the destination) on the text's characters, shown navy (`InlineStyle.linkColor`, lighter in dark mode) and underlined, with the destination as a tooltip (`+Links`). The header's link button and Insert > Link (⌘K) ask for the destination and link the selection, or edit or remove the link the caret is in; with neither, the destination is inserted as the text. Typing continues a link only strictly inside it (`linkForTyping`). `NSAttributedString.Key.inlineFormatting` is every inline key, which code blocks have none of.
- **HTML comments:** each `<!-- -->` is one U+FFFC attachment character drawing nothing (`HiddenAttachmentCell`), carrying `.markdownComment`, the comment exactly as written, which saving and copying write back. A line of only comments gets `HTMLComment.hiddenLineStyle` when loaded, so it takes no space. So does a line that is exactly Leanpub's `{begin-hanging-paragraphs}` or `{end-hanging-paragraphs}` (`hiddenLines`), shown as one hidden attachment carrying its text as `.markdownComment`. The subscript and superscript buttons each take off the other. Typing takes the styles of the character before the caret; a button pressed with no selection is kept in `typingStyles` until the caret moves. Saving writes the styles line by line with `InlineMarkdown`, which puts spaces outside the delimiters and escapes literal `*`/`~` only when needed. Emphasis that changes mid-word (italic straight into bold) can't always be written as Markdown; the text survives but the styles may not.
- **Code blocks:** lines in the `.code` block style, kept exactly as typed: no inline styles (normalisation strips them, and the style buttons skip these lines) and no shortcuts. A non-plain fence is `.codeFence` on every character of its block, so splitting and joining lines keep it, and a change of fence between code lines starts a new block when saving. Return at the end of a code line makes another; on an empty last line of a block it ends the block. Typing ```` ``` ```` (or ```` ```lang ````) alone on a line and pressing Return starts a block. `emptyLineFence` goes with `emptyLineStyle` for an empty last code line.
- **Quotes:** lines in the `.quote` block style, indented (`BlockStyle.quoteIndent`) with a bar down their left drawn by `EditorLayoutManager`, saved after `> `; an empty quote line is `>`. They take inline styles. `> ` typed at the start of a paragraph (`convertQuotePrefix`; a `>` alone waits for the space, though a pasted `>` line converts) or Quote in the style popup makes one. Return at the end of a quote line starts another; on an empty last line of a quote it ends the quote. Backspace at the start of a quote line makes it a paragraph. Copying a whole quote line writes its `> `.
- **Tables:** shown as a grid, like a word processor's: an `NSTextTable` (full width, thin borders, header shaded) with one paragraph per cell, row by row, each ending in a newline and carrying an `NSTextTableBlock` in its paragraph style, `.blockStyle` `.table`, and in the header `.tableHeader` (bold, read by `applyInlineStyles`). The delimiter row isn't shown; its alignments become the cells' paragraph alignment. Cells take inline styles. `+Tables` builds them (`tableText`, from `MarkdownTable.Table`) and writes them back (`markdownTable(of:)`, then `MarkdownTable.lines(for:)`, which pads the columns), so saving reformats a table's Markdown. `tableBlock(at:)` / `isTableLine` / `tableLines(around:)` find cells. `updateTables(in:)` re-derives every cell's block (row, column) and header from its order after each edit. `allowsTableEdit` (from `shouldChangeTextIn`) stops edits merging cells or joining a line onto one, and types a newline inside a cell as a space; NSTextView itself splits a deletion across cells into one per cell, so it empties them, while a deletion covering a whole table and text around it removes it. The header's table button (next to the link button) and Insert > Table… (`insertTable(_:)`) show a popover below the button (`TableSizeController`: "Cols:", a number field with a stepper, 1–20, also stepped by the up and down keys, and an Insert button), which starts at the last number chosen (`tableColumns`, not saved across launches); `insertTable(columns:)` inserts a header and one row on the caret's line if empty, else below it. Tab / Shift-Tab select the next / previous cell; Tab in the last cell adds a row. Return adds a row; in an empty last row it ends the table. Paragraphs that form a Markdown table, typed or pasted, become one when an edit adds a newline (`convertTables`). The style popup is disabled in a cell. A table at the end of the document is followed by an empty line, so saving adds a final newline.
- **Heading IDs:** `.headingAnchor` (a `HeadingAnchor`) on every character of a heading's line, not shown (`+HeadingIDs`); the Markdown view shows them, which is where they are edited by hand. Normalisation spreads a line's anchor over the whole line, and `keepHeadingAnchorsSingle` keeps an ID on one line when a heading is split or pasted into (of adjacent lines with the same ID, the first with text keeps it). Typing attributes carry the caret line's anchor. Only headings write theirs, so a heading made a paragraph and back keeps its ID. A heading whose text has all been deleted (`isTitledHeading` is false) is saved as an empty line, without its `#` or ID, and counts as deleted, though its line keeps the ID, so typing a new heading there gives it the ID back. `{#id: x}` or `{#x}` typed or pasted alone above a heading, or `{#x}` at its end, becomes its ID (`convertAnchorLine`, `convertTrailingAnchor`), unless another heading in the document has that ID (a heading copied rather than moved). Copying a whole heading line writes it as Markdown, with its ID, so cutting and pasting a heading keeps its ID; part of one is copied as text. Saving (`MarkdownDocument.save(to:...)`, before the save starts so the Markdown view's inserted lines don't leave the document edited) calls `addMissingHeadingIDs`, which gives each heading without an ID a new one from `Settings`, unlike every ID in the document and the project's other Markdown files (`ProjectWindowController.markdownFiles()`: open documents as edited, the rest from disk). IDs already there are never changed. In the Formatted view that sets attributes without undo; in the Markdown view it inserts the text undoably.
- **Cross links:** the header's bookmark button (next to the link button) and Insert > Cross Link… (⇧⌘K) show `CrossLinkController`, a popover headed "Insert Cross Link" listing headings (`crossLinkTargets()`: this document's, then, unless `Settings.crossFileLinks` is `off`, those of the project's other Markdown files, headed by file name). `link(to:)` links the selection to the heading's ID, or with no selection inserts the heading's title linked. The destination is `#id`, or with `withPath`, `other.md#id` for another file (`relativePath`, from the document's folder). A heading without an ID gets one first (`MarkdownDocument.headingID(at:settings:)`, whether or not saving adds them), which leaves its document edited; a file not yet open is opened (`MarkdownDocument(contentsOf:)`, added to `NSDocumentController` and `ProjectWindowController.adopt`, not shown).
- **Broken links:** after every change to the text (`textStorage(_:didProcessEditing:)` calls `scheduleLinkCheck`, which runs `checkLinks` once the change is over), when the editor appears and when the project's folder changes (`.markupProjectFilesChanged`), `markBrokenLinks` highlights links to headings that aren't there in red (`InlineStyle.brokenLinkColor`, like highlight's yellow), as a temporary attribute of the layout manager, so the text and undo are untouched (`brokenLinks`; the tooltip says why). `#id` is found among this document's headings, or with `crossFileLinks` `idOnly`, any in the project; `other.md#id` in that file, from the document's folder. Other files' IDs come from `ProjectWindowController.headingIDs()`: open editors' current headings, or the files as read from disk, kept (`filesOnDisk`) until the folder changes. `headingTitles` holds the headings as the last check found them; when an edit removes headings (deleted, or made paragraphs) that links go to (`linkPlaces(to:)`: this file's, and the project's other files' that go here), `DeletedHeadingBar` shows below the header: "3 links go to “Here”, which was deleted.", with Undo, Show Links (a menu of the links; choosing one selects it, `selectHeadingLink(number:)`, opening its file in the project) and close. The next edit hides it. Nothing is checked in the Markdown view; switching views and `load(markdown:)` start afresh (`resetLinkCheck`).
- **Front matter:** not in the formatted view's text at all. `load(markdown:)` keeps it in `frontMatter`, exactly as written (with its newline, if text follows), `formattedText(fromMarkdown:)` leaves it out (so printing does too), and `markdown` writes it back first, adding a newline if it ended the file and text has been typed since. While there is some, the header shows `frontMatterBadge` (a `BadgeButton`, tinted like a variable, left of the link button): its tooltip shows the YAML, and clicking it (`showFrontMatter`) switches to the Markdown view at the top, where it is edited as text. Switching views offsets the caret's Markdown line by `frontMatterLineCount`.
- **HTML tags:** `<br>`, `<img>`, `<p>` and `</p>` (`HTMLTag`, `HTMLTag+AppKit.swift`), exactly as written, which saving and copying write back; other HTML stays text. `<img>` is an image, as below, carrying `.markdownImage`. The others carry `.markdownHTML`: `<br>` with text after it on its line is a U+2028 line separator, which breaks the line where it is without ending it (lines are paragraphs), and at the end of a line, where the line ends anyway, a hidden attachment; `settleLineBreaks` swaps one for the other as edits move text after one or take it away. `<p>` and `</p>` are hidden attachments, and a line of only them and comments gets `hiddenLineStyle`. So are formatting tags, and the text between an opening one and its closing one on the same line carries `.htmlFormat` (a `Set<HTMLFormat>`), which `applyInlineStyles` turns into bold, italic or that heading's font, though the line stays a paragraph (no ID, not a cross link target) and saving writes nothing for it. It follows from the tags: `formattedText` applies it (`applyHTMLFormats`), and normalization re-applies it to edited lines whose formats no longer match their tags (`hasHTMLFormats`), undoably. The Bold and Italic buttons don't see it. Typed or pasted tags convert (`convertHTMLTags`, after comments). CommonMark wouldn't read Markdown inside an HTML block, but the editor does.
- **Images:** `![alt](path)` (parsed by `MarkdownImage` in MarkupCore) is one U+FFFC attachment character carrying `.markdownImage`, the image's Markdown exactly as written, which saving and copying write back. View > Reload Images (`reloadImages`) replaces every image's attachment with one read from disk again. Its `ImageAttachmentCell` (`MarkdownImage+AppKit.swift`) draws the image at its actual size for now (wider images run past the window's edge), or an "Image not found" placeholder. With `Settings.centersImages`, which `EditorLayoutManager.centersImages` carries (printing too), an image alone on its line (`ImageAttachmentCell.isAloneOnLine`: everything else there white space or hidden comments and HTML tags, and not a table cell) is centred: its cell takes the rest of the line and draws the image in the middle, so the text and Markdown are untouched. No image has alignment of its own yet; Leanpub's and HTML's will count as formatting there. The header's image button (`+Images`) inserts an image chosen from anywhere, by typing its Markdown and letting the shortcut convert it. `imagePath(for:)` writes the shortest path relative to one of `imageFolders` that the lookup resolves to that same file (so just the name for an image directly in one of them), or else the full path.
- **Variables:** a variable (`MarkupTag`, kind `.variable`) is one U+FFFC attachment character carrying `.markupTag`, whose `TagAttachmentCell` (`MarkupTag+AppKit.swift`) draws the value in the character's font and colour on a blue tint, or red (`InlineStyle.brokenLinkColor`) for `??`, the value of a variable with none; the tooltip names the variable. Saving and copying write its Markdown. Variables in code blocks are tags too (`MarkupTag.codeText` for code lines, when loading and pasting blocks; `convertTags` runs on code lines, for variables only), which saving writes after a template (`CodeTemplate`); `@name@` converts in code only when the project has that variable, since `@` is common in code. Nothing converts in inline code, which has no template, so it would show the comments. Values come from the project folder's `variables.txt` and, for now, `tags.txt` (exactly those names; `variables.txt` wins; `ProjectWindowController.variableValues()`, read again once the folder changes): `updateTags()` sets them as an edit that can be undone (marking the document edited) when the editor appears, when the folder changes and on switching to the Formatted view; the Markdown view's text is left alone. A document outside a project keeps its values. Insert > Variable… (`insertVariable(_:)`) shows `VariableController` at the caret, "Variable:" with a combo box of the variables' names, and types the variable's Markdown, which the shortcut converts (`convertTags`, which gives typed or pasted variables and citations the current value). With `Settings.quickVariables`, `@name@` typed becomes the variable (not after a letter, digit or `@`, so email addresses are left alone). Citations work the same way, from `bibliography.txt` (`ProjectWindowController.bibliography()`), showing `[n]`, or `[??]` in red; Insert > Citation… (`insertCitation(_:)`) shows `CitationController`, a pop-up of the entries by section. Insert > Bibliography (`insertBibliography(_:)`, enabled with a `bibliography.txt`) writes the bibliography on lines of its own (the marker lines hidden, as comment-only lines are), and `updateTags()` rewrites each one in the text (`bibliographyRanges()`, compared through `markdownLines(from:to:)`) when it differs from the file. Insert > Update Variables in Project (`ProjectWindowController.updateVariablesInProject`, enabled with a `variables.txt`, `tags.txt` or `bibliography.txt`) updates open documents and rewrites the project's other Markdown files on disk.

`load(markdown:)` and `markdown` convert between the text storage and `MarkdownCodec` lines. Copying writes the selection as Markdown (`plainText(for:)`): inline styles, list markers, whole headings and quote lines, and whole code lines as a fenced block (`MarkdownCodec` writes the fences); part of a code line is as typed. Pasting (`paste(_:)`, the text view's `pasteHandler`) inserts the text as typing does, with `insertText` and the typing attributes, so it converts Markdown through the same path; NSTextView's own paste would give the text the attributes of the character before the caret, which in an empty list item is its marker, and the text would be deleted as stray markers. Lines pasted into a list item become items of its kind and level (`continueList(_:overLinesPastedFrom:)`, a ticked item's new ones unticked), as if Return had been pressed between them, the text after the caret going on the last; lines the pasted Markdown made items or headings stay so. Fenced code blocks are the exception, which `pasteCodeBlocks` (in `+Code`, using `MarkdownCodec.pieces(of:)`) inserts as code lines on lines of their own, so that their text isn't converted; one pasted into a code line goes in as its lines. The text view is still `isRichText = false`, so users can't add any other formatting.

Invariants that the controller maintains:
- **Lines stay consistent.** `textStorage(_:didProcessEditing:)` makes a line that starts with a marker carry its item's attributes throughout. Any other line gets one block style (from its first character) and no list attributes. This handles joined lines and deleted markers. It changes attributes only.
- **Typed Markdown syntax becomes styles.** `shouldChangeTextIn` records the edit and `textDidChange` acts on it (`applyMarkdownShortcuts`): `# ` to `###### ` → that heading (on any non-list line), `- ` → bullet, `[ ] `/`[x] ` after a bullet → checkbox, `*italic*`, `**bold**`, `~~strikethrough~~`, `` `code` ``, `~subscript~`, `^superscript^`, `==highlight==` anywhere → styled text (a just-typed closing `*`, `~`, `` ` ``, `^` or `=` waits for the next character, so `**` isn't taken as italic and what follows isn't styled; nothing converts inside inline code or after an unclosed backtick), `![alt](path)` anywhere → image, `[text](destination)` → link, `<!-- -->` → hidden comment, and stray markers inside a line are deleted. These are text changes, made through `replaceCharacters(in:with:)` so NSTextView registers the undo. They trigger only when the edit touches the syntax itself. Lines are processed top-down, so the nesting limit (at most one level deeper than the item above) sees converted lines.
- **The caret never rests before a marker.** `willChangeSelection` moves it after the marker. Moving left from there jumps to the previous line.
- **Typing attributes follow the caret's line.** They are reset on every selection change, and the popup is updated to match. An empty last line has no characters, so a style chosen there (from the popup or a typed `# `) is kept in `emptyLineStyle` for that caret location, and forgotten once the caret is anywhere else.
- **Commands:** Return (`doCommandBy`) adds a table row, continues a list (a new checkbox starts unticked). On an empty item it outdents the item, or ends the list at level 0. At the end of a heading it starts a paragraph. Tab and Shift-Tab move between table cells, or change list level. The popup turns list lines into the chosen style.
- **Every attribute change is undoable.** Changes go through `changeAttributes(in:_:)`, which registers an undo that restores the previous attributes and registers its own redo. It calls `breakUndoCoalescing()`. Normalisation and shortcuts are skipped while undoing or redoing.
- **The controller's `undoManager` is the document's.** It is overridden, and also returned to the window, so all edits mark the document edited.

### Projects

File > Open Project (`AppDelegate.openProject`) opens a folder in a `ProjectWindowController`: an `NSSplitViewController` whose sidebar item (`ProjectSidebarController`, an `NSOutlineView` source list, at least 200 points wide) shows the project folder as its one top row (`rootNode`, its name in bold, open at first; it can be closed, and reloading keeps it as it was), and inside it, folders opening and closing, lists subfolders, `.md`/`.markdown` files and any other file whose type conforms to plain text (which opens as plain text), skipping hidden files and packages, and whose other pane shows one document's editor. View > Hide Sidebar is the split view controller's `toggleSidebar:`. `DirectoryWatcher` (FSEvents) reloads the outline when the folder changes, keeping open folders and the selection.

- Right-clicking the sidebar shows its menu (`ProjectSidebarController.makeMenu`, each item targeting the project window and carrying the item clicked, or the project folder below the rows): New File… and New Folder… ask for a name in a sheet ("Untitled.md", "untitled folder", numbered if taken; a file name without an extension gets `.md`) and make it in the folder clicked, or the clicked file's folder, opening a new file; Duplicate copies a file or folder beside it as Finder names copies ("a copy.md", "a copy 2.md"); Rename… asks for a new name, starting from the current one (`rename(_:to:)`; a change of case alone is allowed), and the documents open in the window from it follow it, unsaved changes and all, though links to it from other files aren't changed; Delete moves it to the Trash (`moveToTrash`, which tests replace), asking first if it holds files open in the window with unsaved changes, and closes those (`forget`). The project folder can't be duplicated, renamed or deleted. Selecting a file (`select`) opens the folders on its path from the top, since the outline knows only the items of open folders. `ProjectWindowController+Files.swift`.
- Choosing a file opens it through `NSDocumentController` with `display: false`, so the document has no window controllers, sets `document.project`, and swaps its editor into the pane. Documents opened in the window stay open, with unsaved changes and undo, while others are shown; the sidebar marks those with unsaved changes (documents post `.markdownDocumentEditedChanged`).
- The project window controller isn't any document's window controller. Document actions (Save, Save As, Print...) reach the document shown through `supplementalTarget(forAction:sender:)`, and the window delegate returns that document's undo manager. A document's `showWindows` (File > Open of a file already open in a project) shows it in its project instead of making a window. A file that already has its own window is brought forward rather than shown in the project.
- Closing the window asks about each document with unsaved changes in turn (`canClose(withDelegate:...)`), then closes the documents.
- The project windows open at quit are opened again at launch: `applicationWillTerminate` saves each one's folder and shown file in `Settings.openProjects` (key `MarkupOpenProjects`), and `reopenProjects` opens those folders that still exist, showing the file if it still exists. The files open in windows of their own are reopened too: `applicationWillTerminate` saves them, front to back, in `Settings.openDocuments` (key `MarkupOpenDocuments`; `windowedFiles(in:)`, from `NSApp.orderedWindows`, leaves out untitled documents and those in projects), and `reopenDocuments` opens those that still exist, the frontmost last. macOS's own window restoration would do this only with "Close windows when quitting an application" turned off. Each file's window keeps its frame (`setFrameAutosaveName`, `MarkupDocument <path>`, in `makeWindowControllers`). NSDocumentController can't open documents in the test runner (it doesn't declare the document types), so tests can't check the files being reopened. When there are any projects or files to reopen, no untitled document is opened (`applicationShouldOpenUntitledFile`).

### Settings

Markup > Settings (`SettingsWindowController`, opened by `AppDelegate.showSettings`) edits `Settings`, which keeps app-wide settings in user defaults. Tests give it a throwaway `UserDefaults` suite.

- **Heading IDs:** `addsHeadingIDs` (key `MarkupAddsHeadingIDs`, on by default), `headingIDForm` (`MarkupHeadingIDForm`, default `idLine`) and `headingIDScheme` (`MarkupHeadingIDScheme`, default `fileLevelWord`). They apply to new IDs only, including those cross links add. `crossFileLinks` (`MarkupCrossFileLinks`): `idOnly` (`#id`, as Leanpub needs; the default), `withPath` (`other.md#id`) or `off` (only the same file's headings).
- **Quick variables:** `quickVariables` (`MarkupQuickTags`, its key from when variables were tags; off by default): typing `@name@` inserts the variable.
- **Bibliography:** `hangingBibliography` (`MarkupHangingBibliography`, on by default) writes bibliographies inside Leanpub's hanging paragraphs.
- **Line numbers:** `showsLineNumbers` (`MarkupShowsLineNumbers`, off by default; set from View > Show Line Numbers, and setting it posts `.markupShowsLineNumbersChanged`).
- **Centre images:** `centersImages` (`MarkupCentersImages`, on by default; setting it posts `.markupCentersImagesChanged`, and editors lay out again).
- **Images directory** (`imagesDirectory`, key `MarkupImagesDirectory`, a folder path or unset). Image paths are looked up in this folder first, then the document's own folder, then its `resources` and `images` subfolders, then its parent, `..` (`Settings.imageFolders(forDocumentAt:)`). A path starting with `/` (a website's root, as in Jekyll's `/assets/a.png`) is looked up without it, and failing that is the file at that full path, as Insert Image writes for an image in none of the folders; the text keeps its `/` (`MarkdownImage.fileURL(in:)`). A `//` path is a web address.

### Updates

Markup > Check for Updates uses Sparkle (a package dependency; its tools, such as `generate_keys` and `generate_appcast`, are in `.build/artifacts/sparkle/Sparkle/bin`). `Updater` makes Sparkle's standard updater controller only in an app bundle whose `Info.plist` has a `SUPublicEDKey`; otherwise (`swift run`, tests) there is none and the menu item is disabled. The feed is `SUFeedURL`. The executable has the rpath `@executable_path/../Frameworks` for the bundle; `swift run` finds the framework next to it.

### Printing

File > Print (`MarkdownDocument+Printing.swift`) prints the document formatted, whichever view the window is in. It builds a separate text view from the document's current Markdown with `formattedText(fromMarkdown:)`, the same conversion `load(markdown:)` uses. The view is as wide as the page between the margins, and has the light (aqua) appearance so text prints dark in dark mode.

### Markdown view

The header's Formatted / Markdown switch (`+ViewMode`) replaces the text storage with the raw Markdown, in a monospaced font, and sets `isShowingMarkdown`. In that mode `markdown` returns the text as is, and the formatting machinery is off: normalisation, shortcuts, `doCommandBy` (so Return and Tab behave as plain text), the caret-before-marker rule and the style popup. Switching back runs `load(markdown:)`. Both views have one line per Markdown line, except that a table has a line per cell in the formatted view, so the caret is carried across as (Markdown line number, distance from line end), into the start of a table's row or cell. Switching clears the undo stack, because undo steps hold ranges in the other view's text. This doesn't change the document's edited state. Copying in this view copies the text as it is. With `Settings.showsLineNumbers`, the scroll view's vertical ruler, a `LineNumberRulerView`, numbers the lines, beside each one's first line fragment (`updateLineNumbers`, which shows it only in this view, plain text included); it widens to fit the largest number after each edit.

### Plain text

A file whose extension isn't `.md` or `.markdown` (`MarkdownDocument.isPlainText`, decided in `read(from:ofType:)` by extension, because another app's `.md` type arrives as plain text) gets an `EditorViewController(plainText: true)`. It starts and stays in the Markdown view (`setShowingMarkdown` does nothing, View > Show Markdown is disabled), its header hides every control and shows a "Plain Text" label (`plainTextLabel`) instead, and `load(markdown:)` and printing show the text as it is. New documents are Markdown.
